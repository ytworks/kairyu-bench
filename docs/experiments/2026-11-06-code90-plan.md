# コード90点超へ向けた再開契約（2026-11-06）

## 90点の意味とデータの役割

- 主たる追跡対象は、前回82.5476点だった固定64コード項目。HumanEval+20、MBPP+20、LiveCodeBench14、SciCode10の**公式4source等重み平均**で、丸め前の値が90を超えることを目標とする。問題の削除、source重み変更、短い3source版への置換で達成としない。
- この64項目は既に成績を見た固定参照であり、未見・独立holdoutとは呼ばない。候補方向の作成はdevと自作校正で行い、参照集合のgold/reference実装を学習に入れない。最終候補は同条件で2回確認し、都合のよい1回だけを選ばず両回の公式値を示す。
- 開発用の主測定は公式dev30のコード90項目：HE30、MBPP30、LCB20、SciCode10。SciCodeを含まないdev10の3sourceスコア90超を目標達成にはしない。10/30/60分版は段階選抜に使い、すべての候補へ重い全体ベンチを繰り返さない。
- 別の確認候補集合を、既存manifestのtest60−test30からmetadataだけで固定する。既知group重複19、未解決cross-source91を除き2,393項目、コード108（HE30/MBPP30/LCB30/Sci18）。原モデルで過去に評価・校正された集合なので、これも「一度も評価されていない」とは呼ばない。今周期の候補選抜にはその結果を使わない。最低限コード108の転移結果を別記し、残る領域の実行範囲・欠測を明示する。
- 全領域の得失はfull dev10等で追う。コードの改善と無関係な能力の多少の低下はユーザー方針に沿って許容し、領域別・項目別に記録する。単一の合計点で重大な実装退行を隠さない。
- 推論はnative thinking ON、既存公式generation設定。比較途中でeffort・token上限・採点方法を有利に変更しない。

## 変更セットと実験順

[Opus 5.5の匿名方法レビュー](anonymous-code90-review-2026-11-06.md)を受け、以下の8案を保持する。これは候補方針であって、8つの有効な重みが既に得られたという意味ではない。

| 案 | 目的と機構 |
|---|---|
| A | 多段科学計算：数値不変条件、配列状態、段階間参照をMLPとattentionの共同方向へ |
| B | 実装契約・既存機能保全：改善目的と一緒にinterface/非破壊性を保護 |
| C | 境界条件・論理：独立した実行反例・metamorphic検査から行列方向を作る |
| D | tool引数・状態：call/no-call、型、optional値、複数turn終了状態を分ける |
| E | 学習済みdonorの構造group：base同一性と未知の学習重複を確認し、全面mergeの再試行を避ける |
| F | 検証から提出：文章上の完了でなく、実際のrepo/提出artifactで判断 |
| G | 費用とBF16実現：nativeだけに偏る絶対L2と、役割/実branch摂動を区別 |
| H | 必要な場合の実行検証付き低ランク学習：独立した科学コードから方向を作り、merge後のBF16重みを評価 |

最初はA+Cの実行信号とBの保全を中心にする。既存のraw-next-token matrix勾配を、公式chat frameの公開回答全tokenの目的へ拡張する。短いmargin/NLLの上昇だけで採用しない。native-only、matrix-only、jointや構造groupを分け、6案以上を同一ロードで比較する。新しい方向がなければ同じ微小振幅gridに時間を使わない。

モデル内の構造は実config/codeで確認する：60層、hidden5376、MLP21504、5 sliding＋1 full attentionの反復、tied embedding、final softcap30。重みnormだけから機能を同定しない。初回gradient pilotは512token以下で、真matrix勾配とzero-additive probeの一致・GPU peak memoryを確認する。未検証のcheckpoint再計算hookを黙って有効にしない。

独立科学校正は自作のcorrect/foilと数値・shape・非破壊契約をCPUで検証し、学習familyと転移確認familyを分離する。WSP答案や隠れたreasoningは用いず、校正の成功を公式WSP点に混ぜない。低ランク学習を使う場合は学習量・rank・対象行列・保全項・データsplitを別途固定し、実際のBF16 mergeで効果が残ることを確認する。

改善した候補の保存weightsを次の親として積み上げる。新しい差分だけを親へ加えて一度丸め、既に採用した差分を二重加算しない。親のpath・tree・採用履歴を固定し、原モデルへ編集元を戻さない。最後にgroup除去で必要な変更を検証する場合も、採用済みの効果を保持できるかを別候補として測る。全候補のcheckpointコピー・配信再起動は避け、選抜後だけ保存・公式WSPへ進める。

## 方針追補：改善したモデルを次の起点にする（2026-11-06）

ユーザーの「改善したら改善後から積み上げる」という明示指示に合わせ、
以後は現在の作業モデルを起点に候補を作る。同条件の主目的スコアが改善した候補へ更新し、
悪化した候補なら直前の作業モデルを保持する。関連能力の得失は個別に報告し、
多少の他領域損失は許容する。CIは不確実性の説明として示すが、有意差や全領域非退行を
作業モデル更新の追加条件にしない。

今回の4条件dev90ではPが73.825397点、fresh original Oが71.186508点だったため、
Pを作業モデルへ更新した。Pへ固定Dを加えたMは67.908730点でP比−5.916667 ppとなり、
Mへは更新せずPを保持する。[4条件の結果と時系列](2026-11-06-public-base-alignment-fourway-m.md)に
科学的比較と作業上の判断を分けて記録した。

次の候補作成前には、working-incumbent.jsonのSHA、checkpoint path、treeを読み固定し、
specのbaseと実際の入力weightsをその作業モデルに一致させる。現時点のPは
checkpoints/code90-heretic-public-base-official-protocol-v1、
tree 3dfb3bd1db0ab2ba4fff843616bb0d3109e0b97a6c9349658620908f2a24bebc。
新しい差分はこの保存値を起点に一度だけ丸め、original Oは不変の比較参照として保持する。
従来のsource identity・保存byte検証は引き続き行う。

これは探索の進め方の修正であり、既知64項目の90点超、未知問題への一般化、
全領域・DeepSWE・HF条件の達成を宣言するものではない。
Pのそれらの確認は未実施である。Mの公式reportは方針監査前に既に完成しており、
恒久的な方針記録は4条件の全report完成後に作られた。
ユーザー指示が担当者によるM scoreの初回閲覧より前だったことと、
