# weight space programming 用の共通評価ベンチマーク（10分・30分・60分、`wsp`）

状態: **2026-11-04 オーナー承認済み（検証計画を含む）。** main から作成。
kairyu 側の変更（Gemma 例の重み差し替え設定）は ytworks/kairyu PR #669
（計画 `docs/superpowers/plans/2026-11-04-gemma-edited-checkpoint.md`）。

## Context（なぜ作るか）

- Weight-Space Programming（MIT CSAIL、2026-11-02 の公開記事）は、LLM が勾配を使わず
  重みを直接書き換えてモデルの性質を変える手法。記事は MATH-500・GSM8K・IFEval など
  一部の能力しか見ておらず、作者も「ベンチマークを作っている途中」と書いている。
  編集は狙った能力を上げても、他の能力を壊すことがある（編集・マージ・圧縮の研究で共通の指摘）。
- そこで「編集した重みが何を得て何を失ったか」を、どの編集手法にも同じ物差しで、
  GPU 上 10分・30分・60分で測れる共通ベンチマークを kairyu-bench に作る。
- 決定済み（オーナー回答）:
  - 時間の基準: Gemma 4 31B・8GPU（既存 `gemma-4-31b-8gpu` 構成: 2GPU×4台、MTP 4、
    vLLM v0.33.0 overlay、公式サンプリング temperature 1.0 / top_p 0.95 / top_k 64、思考あり既定）
  - 置き場所: kairyu-bench（新しい実行パターンとして追加）
  - 問題は「調整用（dev）」と「最終確認用（test）」の2組に分ける
  - 時間は起動完了後の評価だけ（起動時間は別に記録。実測 107〜132 秒）
  - 編集版の起動: `gemma-4-31b-8gpu` に重みの場所の差し替え設定を1つ足す（kairyu の example 変更）
  - LLM の審判が必要なベンチマークは外す（会話の質と幻覚は測らない）

## 設計の原則（5つ）

1. **どのパターンも全14能力を測る。** パターンの違いは「問題数（精度）」と「1問の最大長（深さ）」。
   10分版 ⊂ 30分版 ⊂ 60分版 の入れ子にし、60分の結果から10分・30分のスコアも出せるようにする。
2. **採点に LLM を使わない。** 正解照合・テスト実行・規則チェック・対数確率だけ。
   編集したモデル自身に採点させると、採点も一緒に壊れるため。
3. **元モデルとの比較を主役にする。** 同じ問題で元モデル（Gemma 4 31B）と編集版を並べ、
   能力ごとの差と 95% 信頼区間、「正解→不正解」「不正解→正解」に変わった問題数を出す。
   正解率の差が小さくても、入れ替わりが多ければ中身が変わっている（先行研究の指摘）。
4. **スコアは出力だけで決まる。** 時間切れで採点を変えない。代わりに問題ごとの出力上限
   トークンを固定する（上限到達は不正解、到達率は別に報告）。実行時間は記録する。
5. **問題の選び方は層別の無作為抽出（固定シード）。** 既存の「先頭 N 問」は易しい問題や古い
   問題に偏るため使わない。dev と test は同じ構成で重ならない。

スコアに入れない診断（すべてのパターンで出す）:
- **重みの健全性**: 英語（WikiText-2）・日本語（Wikipedia）・コードの固定文章で、元モデルとの
  次トークン分布の差（KL）と最有力トークンの一致率、perplexity。生成なしで安く、壊れを最も早く検出する。
- **生成の健全性**: 上限到達率、空回答・形式違反の率、平均出力長（記事で最も効いた指標）。
- **確信度の正しさ**: 選択式問題の対数確率から校正誤差。
- 消費トークン数、API コール数、実行時間。

総合スコア = 14能力の単純平均（能力ごとに同じ重み）。

使わないもの（理由）:
- HLE、CharXiv、τ-bench banking: 採点や利用者役を対象モデル自身が行う（原則2に反する）
- 会話品質（Arena-Hard、MT-Bench）、SimpleQA: LLM 審判が必要
- DeepSWE、Terminal-Bench 4.0: 1問で60分を超える（DeepSWE 平均 47〜100分、TB4 は最大8時間）
- SWE-bench Verified: kairyu-bench で完走した実績がない（SWE-bench Pro で代替）
- HarmBench、StrongREJECT: 採点用の別モデルを GPU に載せる必要がある
- JMMLU、Multi-IF: 改変禁止・非商用ライセンス（AIME / HMMT は非商用なので研究用途として記録する）

## 時間の組み立て

- 見積りの前提: Gemma 例の短い入力・32並列の実測 1,576〜1,950 tok/s（4台合計）。
  8割まで詰めると出力 約100万（10分）/ 300万（30分）/ 600万トークン（60分）。
- 1問の最大長は「その問題が単独で時間内に終わる長さ」で決まる。目安 8〜16K / 32K / 64K。
  元モデルがこの長さで解き終わらない問題はそのパターンに入れない（10分版は短く解ける問題が
  中心になり、長く考える問題は30・60分版で増える）。
- 長い問題とエージェント作業を最初に投入し、残りで GPU を埋める（全体の終了を早める並べ方）。
- データ取得・Docker イメージ・タスクイメージは事前の `prepare` で用意し、時間に含めない。
- 編集版が長く考えすぎて時間を超えても採点は変えず、「時間超過」として報告する（原則4）。

## 実装（kairyu-bench、`kairyu/` は変更しない）

使い方:
```sh
./kairyu-bench wsp prepare --tier 60
./kairyu-bench wsp run http://host.docker.internal:8020/v1 --tier 10 --split dev
./kairyu-bench wsp compare results/<元モデルの run> results/<編集版の run>
```

追加するもの:
- `src/kairyu_bench/wsp/`: 能力と出典の対応、問題選択（層別・入れ子・dev/test）、並列実行
  クライアント（4台を埋める並列数、問題ごとのトークン・時間記録、固定シード）、採点（各出典の
  公式チェッカーを使う: IFEval/IFBench/BFCL/evalplus/math-verify/BBEH/LCB/SciCode/MRCR）、
  対数確率の診断、比較レポート（対応のあるブートストラップ、入れ替わり数、総合スコア）
- `src/kairyu_bench/data/wsp/`: 確定した問題リスト `{10,30,60}-{dev,test}.json`（問題 ID・上限・シード）。
  入れ子・dev/test の重なりなし・件数は読み込み時に検査する
- 既存の再利用: `direct.py` の GPQA 選択肢並べ替え・LongBench・MRCR 採点、LiveCodeBench と
  SciCode の公式テスト環境、Terminal-Bench 2.1（Harbor）と SWE-bench Pro の実行（問題 ID 指定を追加）
- `benchmarks.json` に新しい出典の固定 revision、runner イメージに依存追加
- `docs/wsp.md`（使い方・能力表・採点・時間・限界）、README に節を追加
- テスト（テスト方針どおり最小限）: 新しい採点器ごとの「入力→得点」、比較レポートの出力
- 元モデルの結果は結果ディレクトリに保存し、`compare` が KL・入れ替わりの基準に使う

kairyu リポジトリの変更（承認済みの構造変更、example 所有、`kairyu/` は変えない）:
- `examples/gemma-4-31b-8gpu`（`run.sh`・`control.py`・`compose.yaml`・README）に「チャット用
  チェックポイントの場所を差し替える」設定を1つ追加する。編集した重みを基準と同じ構成
  （2GPU×4台、MTP 4、同じ vLLM）で起動するため。差し替えたときは公式の固定ハッシュ検査の
  代わりに、その重みのハッシュを計算して記録し、`/v1/models` の結果と一緒に残す。
  MTP の補助モデルと埋め込みモデルは公式のまま（MTP は検証付きなので出力の分布は変わらない）。
- FN-D9 Gemma amendment と PROGRESS.md に記録。

## 検証計画（GPU）

基準スタックは今動いている `gemma-4-31b-8gpu`（API 8020）をそのまま使う。
編集版の検証ではこのスタックを差し替え設定で再起動する。

| Step | 内容 | 合格条件 | 時間 |
|---|---|---|---|
| 0 | 事実確認: Kairyu 経由で `prompt_logprobs` と `seed` が返るか、短い入力で 64/128/256 並列の総 tok/s と1本あたりの速度 | 値を記録（`prompt_logprobs` が通らなければ `kairyu/` は直さず、診断は vLLM レプリカへ直接送る） | 30分 |
| 1 | 校正: 60分版の候補（dev・test 各 1.5倍）を元モデルで1回、長い上限で実行し、問題ごとの出力長と時間を測る。エージェント作業は過去の実行時間で短い候補を絞ってから測る。結果から上限・件数を決め、問題リストを確定してコミット | 全候補が採点される | 4〜5時間 |
| 2 | 時間と完走: 元モデルで各パターンを dev 3回・test 1回 | 全回で 10 / 30 / 60分以内、全問採点（通信障害だけ再実行） | 約7時間 |
| 3 | ノイズの大きさ: Step 2 の dev 3回どうしの比較 | 元モデル同士の総合差の 95% 区間が 0 を含む（比較の統計が正しい）。能力ごとの回ごとのぶれを記録 | 追加なし |
| 4 | dev と test の同等性 | 元モデルの dev と test の総合スコア差の 95% 区間が 0 を含む | 追加なし |
| 5 | 検出力: 編集版4つ（手元の Quyet-1.0-Large = Gemma 4 31B に LoRA を合体したもの、重みに3段階の小さな乱れを加えたもの）を各パターン dev で1回 | 乱れが大きいほど KL が増える。10分版・30分版の総合スコアの順位が60分版と一致（60分版で差が区間内の組を除く） | 約7時間 |

合計 GPU 約18〜19時間。編集版の重み（1つ 59GB）は NVMe に置き、記録後に削除する。
結果は `docs/wsp.md` の実測節に記録する（wiki は指示があれば）。
